Paper Summary - No Long Context

Created2026-11-10|Updated2026-11-13|Tech
|Post Views:

1. Introduction

Longer context input carries many drawbacks:

Due to the drawbacks of the long context, it seems that the context window should be as short as possible. However the real tendency is the context window is longer and longer now.

So the core question is that:

  • Are long contexts necessary?

The long context window problem is classified into 2 types

  1. LCW1: Workloads of Long Horizon Tasks. Context builds up as the model makes its way towards the completion of the task (ReAct)
  2. LCW2: Workloads of of Long-Input Tasks that require operating across a large amount of input information.

The question is decomposed into three questions:

RQ1: Can long-horizon tasks be completed without long contexts? RQ2: Can long-input tasks be completed without long contexts? RQ3: Can long-horizon tasks be completed taking no more than a single action per context?

2.2 History Compaction Regimes

Full-History Accumulation (FHA).

​ The baseline full-history accumulation regime appends every model action and environment observation to a single conversation for the duration of the task. No history is removed or replaced during a run. This is the default mode of operation for mini-swe-agent and mini-agent.

End-of-Conversation Compaction (EoCC).

​ This regime follows the full-history ReAct loop until the length of the conversational context crosses a pre-specified compaction threshold. The model is then instructed within the active conversation to produce a bounded, task-relevant compaction of its state.

​ A higher total context limit reserves space for this compaction turn and terminates the conversation if compaction does not complete in time. The harness starts a fresh conversation containing the original task and the compacted state, and execution resumes under the same system prompt. This cycle repeats whenever the compaction threshold is crossed. We write these two values as “total context limit / compaction threshold” in tokens.

Single-Action Compaction (SAC).

​ This regime maintains a compact semantic state and essentially no conversational history. Each conversation receives the task and current semantic state, performs exactly one environment action, observes its result, and updates the semantic state.

​ The harness then discards that conversation and starts a fresh one for the next action. For the experiments in Section 5, we apply SAC as a context-management regime to mini-swe-agent; the underlying agent harness, model, and task environment otherwise remain unchanged. SAC therefore keeps the active conversational context shortest of the three regimes and operationalizes the single-action setting of RQ3.

3. RQ1: Long-horizon tasks don’t need long contexts

The authors evaluate EoCC on 6 benchmarks representing long-horizon workloads and measure the performance of EoCC-modified harnesses against their baseline FHA counterparts. The authors sequentially decrease the total context token limit and the corresponding compaction threshold.

In short, this has the effect of lowering the maximum context window needed by the model and of triggering increasingly more frequent compactions while executing long-horizon tasks.

EoCC vs FHA:

  • Result 1: Comparable Performance

    Model Variation Relative to the Baseline
    Opus 4.5 −3.7 ~ +5.6 ppts
    GPT 5.6 Sol −3.3 ~ +4.4 ppts

  • Result 2: Substantial Cost Reduction

    Model Cost Reduction Factor
    Opus 4.5 2.2× – 8.8×
    GPT 5.6 Sol 2.4× – 5.0×

  • Result 3: Failure Mode worried didn’t Happen

    • Failure Mode Worried: Compressing too often → the model redoes work it has already completed / re-reads old information → the total token count ends up higher, eating back the savings.

Conclusion: Long-horizon tasks don’t need long contexts.

Compaction is always along with information loss, so in latter rounds if agent need some information abandoned is impossible. One solution is to create a full memory system to store all history information like the visual memory in VISTA.

Then the LCW1 turns into LCW2 which will be discussed in RQ2.

4. RQ2: Long-input tasks don’t need long contexts

The authors evaluate EoCC on 7 benchmarks representing long-input workloads and measure the performance of EoCC-modified harnesses against their baseline full-input counterparts.

  • The full-input baseline receives the entirety of the input as prescribed by the benchmark
  • The compacting harness uses Bash tools to perform selective reading of inputs from environment filesystem

Benchmarks:

Selected Input vs Long Context:

  • Result 1: Comparable（Often Better）Performance

    Model Variation Relative to the Baseline
    Opus 4.5 −0.4 ~ +40.0 ppts
    GPT 5.6 Sol +1.0 ~ +30.9 ppts

  • Result 2: Substantial Cost Reduction

    Model Cost Reduction Factor
    Opus 4.5 6.5× – 54.6×
    GPT 5.6 Sol 4.4× – 233.3×

  • Result 3: Failure Mode Worried Didn’t Happen

    • Failure Mode Worried: selective reading forces many read calls / re-reads → conversation length grows with document size → total token spend rises and eats the savings.

    • Observed: conversation length stays roughly in a bounded band as document length grows by orders of magnitude (Figures 7/8; the x = y reference rises exponentially, real conversations do not). Median compaction count ≈ 0 — selective reading alone is usually enough.

5. RQ3: Compaction can be performed after every action

This question in fact is discuss about the Single-Action Compaction’s accessibility. The traditional react loop keeps appending messages as time goes by.

The Single-Action Compaction (SAC) method can limit the context window to roughly the size of a single turn by summarizing at the end of each step.
