Paper Summary - GTA1

Created2026-11-05|Updated2026-11-11|Tech
|Post Views:

1. Introduction

This work aims to solve two challenges: Planning and Grounding.

1.2 Planning

Existing work (Aria-ui, OSWorld-G, Agent S, Agent S2, Aguvis) often pair a GUI grounding model with a planner. The planner determines an action proposal at each step, while the grounding model locates the target interface elements for interactions (e.g., click areas).

1.2 Grounding Training Problems

1.2.1 SFT Drawback

Existing grounding models (Aria-ui, JEDI, Os-altlas, Seeclick) predominantly rely on SFT, , which trains models to predict the exact center of target interface elements. This method struggles to generalize to complex and high-resolution scenarios.

Fundamentally, SFT introduces a misalignment with the task itself: any coordinate within the target element constitutes a valid interaction, yet SFT penalizes deviations from the center. It limits model flexibility, reduces robustness, and preventing the model from perceiving appropriate supervision signals.

Some recent works also use GRPO to train grounding model:

2. Multimodal Agent Category

2.1. Two-stage GUI Agent

  • Use advanced reasoning models as planner
  • A separate grounding module

2.2 Native GUI Agent

  • A native GUI agent completes user tasks in an end-to-end manner.

    Four main aspects are studied (Ui-tars):

      1. perception, interpreting the user interface to understand the current state;
      1. memory, storing knowledge and historical experiences to support making decisions;
      1. planning, analyzing the task and reflecting on progress to generate action proposals;
      1. action, performing atomic operations based on the action proposal to effectively progress toward the task goal.

3. GTA1

This work adopts a two-stage GUI agent framework composed of a planner and a grounding model.

3.1 Planning

  1. At each step of executing user instructions, sample K candidate action proposals, denoted as \(\{p_k\}_{k=1}^K\) where \(p_k\) presents a corresponding action. (e.g., clicking ‘the blue button’ or performing a keystroke).

  2. Use a VLM as judge to evaluate the \(K\) candidates \(\{p_k\}_{k=1}^K\) based on their alignment with the user intent and the current GUI state.

    The judge, which can be the planner model itself, picks the best candidate action proposal \(p_{k^*}\)

  3. Grounding model takes the best candidate action proposal \(p_{k^*}\) and current screenshot \(s\) as input. Then grounding model outputs coordinates.

    For non-coordinate-based actions (e.g., key presses or text input), the action can be executed directly without grounding.

3.2 Grounding

3.2.1 Data Preparation

Prepare training data:

  1. Collect open-source datasets to train our model, e.g., the Aria-UI collection.
  2. These dataset’s bbox information comes from A11y or HTML parsers which may introduce noise.
  3. Cleanup the dataset: Using OmniParser, denoted as \(\mathcal M (\cdot)\), to detect all UI elements in screenshot \(s\), , resulting in a set of bounding boxes \(\{b_i\} = \{\mathcal M(s)\}\). Each \(b_i\) represents the bounding box of a detected UI element.
  4. Calculate the IoU of \(b_i\) and annotated bbox value. Drop the invalid entry.

3.3.2 GRPO

Base model comes from UI-TARS-7B and OpenCUA-32B.

4. Conclusion

  1. In two-stage GUI agent (separate planner and grounding model), the tradition agent structure only let ask planner rollout 1 next step action. GTA1 let planner generate 8 candidate actions, then let Judge choose the most appropriate one,
  2. GTA1 is trained by GRPO with single click reward and outperform other models.
